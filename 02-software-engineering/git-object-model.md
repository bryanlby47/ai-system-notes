# Git Object Model

## 通俗解释

Git 是一个版本化的内容数据库。

执行 `git commit`，相当于在本地项目的 `.git` 数据库里创建一个可回到的项目存档点；执行 `git push`，才会把这些本地 Commit 上传到远程仓库。

```text
工作区文件
→ git add
→ 暂存区
→ git commit
→ 本地 .git
→ git push
→ GitHub
```

## 为什么出现

软件项目会持续变化。如果只靠复制文件夹保存版本，很快会出现：

```text
最终版
最终版2
最终版最终版
最终版修复版
```

Git 用可追踪、可比较、可恢复的版本节点管理项目状态。

## 系统模型

Git 的三个核心对象：

```text
Commit
↓
Tree
↓
Blob
```

- **Blob**：保存文件内容，不保存文件名。
- **Tree**：保存目录结构、文件名、权限以及对应的 Blob / 子 Tree。
- **Commit**：保存作者、时间、说明、父 Commit，并指向某个根 Tree。

因此，一个 Commit 逻辑上代表项目在某个时刻的完整快照，但 Commit 对象本身并不装着全部代码。

## Hash 的作用

Git 会根据对象的类型、长度和内容计算 Hash，并把 Hash 当作对象 ID。

```text
Hash = Key
对象内容 = Value
```

Hash 不能反向还原内容。Git 能恢复文件，是因为真实内容已经存进 Blob；Hash 只负责定位和校验。

## 存储方式

第一次提交 1 GB 的全新内容，`.git` 对象库通常也需要保存接近 1 GB 的数据，具体取决于压缩率。

后续提交时：

- 未变化的内容直接复用旧对象。
- 变化后的文件产生新 Blob。
- 文本内容通常压缩效果较好。
- MP4、JPG、ZIP 等已压缩的二进制文件通常几乎压不动。

因此 Git 适合代码和文本，不适合频繁变化的大型二进制文件；后者常使用 Git LFS 或对象存储。

## 删除原始文件会怎样

删除工作区里的文件，不会删除历史 Commit 中的内容。

```text
工作区 = 当前正在编辑的版本
.git = 历史档案馆
```

只要对应对象仍然可达并且 `.git` 没有丢失，Git 就能从历史 Commit 恢复文件。

## 核心 Trade-off

### 历史完整性 vs 仓库体积

保留更多版本提高可追溯性，但大文件和频繁变化的二进制内容会显著增大仓库。

### 本地自主性 vs 云端安全

Commit 默认只在本机；Push 后才有远程备份和协作能力。

## 典型误区

- `git commit` 等于上传 GitHub：错误，上传动作是 `git push`。
- Hash 里压缩了原始内容：错误，Hash 只是 ID，Blob 才保存内容。
- Commit 只保存“修改差异”：逻辑上它代表完整快照；实现上复用未变化对象。
- 删除当前文件会破坏历史：错误，历史内容已经进入 `.git` 对象库。

## 工程与产品启发

Git 的本质可以抽象为：

```text
内容寻址存储
+ 树结构
+ 版本图
+ 状态变更
```

理解 Git，不应只背命令，而应理解工作区、暂存区、Commit 和远程仓库分别代表什么状态。
