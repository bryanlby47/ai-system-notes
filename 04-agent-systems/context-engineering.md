# Context Engineering

## 通俗解释

Context Engineering 是设计模型在这一轮“看到什么”。

Prompt 更像告诉员工做什么，Context 更像给员工准备完成任务所需的材料。

```text
用户问题
+ 系统规则
+ 业务知识
+ 用户状态
+ 历史对话
+ Memory
+ Tool 结果
→ 模型
```

## 为什么出现

很多 Agent 失败并不是因为模型不会推理，而是因为：

- 没看到正确规则；
- 缺少实时用户状态；
- 检索到了无关知识；
- 关键 Tool 结果没有进入本轮上下文；
- 无关信息太多，干扰了注意力。

因此，系统需要动态选择当前推理链真正依赖的信息。

## 核心问题

### 给什么

按当前问题的信息依赖性选择，而不是按业务资料的总体重要性选择。

例如用户问“为什么开不了月付”，优先需要：

```text
用户实时状态
+ 当前生效的准入 / 风险规则
```

营销信息和历史对话虽然可能重要，但通常不是这个问题的决定性信息。

### 什么时候给

- 静态加载：始终放入系统上下文。
- 动态检索：需要时通过 RAG 获取。
- 实时查询：通过 Tool 获取当前状态。
- 记忆召回：在满足触发条件时读取长期 Memory。

### 怎么给

- 原文还是摘要；
- 结构化字段还是自然语言；
- 全量历史还是任务状态；
- 多个来源如何标注优先级、时效性和可信度。

## Context Assembly

优秀的 Agent 通常不会维护一个固定的大 Context，而是动态组装：

```text
识别当前任务
→ 判断信息依赖
→ 选择数据源
→ 调用检索 / Tool / Memory
→ 过滤、排序、压缩
→ 生成本轮 Context Package
```

Router 的输出也可以超越“选择哪个 Agent”，进一步描述：

- 目标 Agent；
- 任务类型；
- 所需 Context；
- 需要调用的 Tool；
- 风险等级；
- 输出约束。

## 核心共识

- Context 质量通常比 Prompt 修辞更影响 Agent 效果。
- Context 越多不一定越好。
- 实时业务状态不应被长期 Memory 替代。
- Context 应围绕当前推理依赖动态组装。

## 核心 Trade-off

### 完整性 vs Token 成本

信息过少导致判断依据不足；信息过多增加成本，也可能让关键证据被淹没。

### 静态上下文 vs 动态检索

静态加载稳定但昂贵；动态检索更高效，但存在漏召回和排序错误。

### 个性化 vs 污染风险

用户画像和长期 Memory 可以提升个性化，但错误或过期信息会持续影响决策。

### 原文准确性 vs 摘要效率

原文信息完整但占用空间；摘要更短，但可能丢失边界条件。

## 典型误区

- 把重要资料都放进去就是好的 Context。
- 长上下文窗口可以消除 Context Engineering。
- 历史对话、Memory 和实时 State 是同一种信息。
- Context 问题可以只靠优化 Prompt 修复。

## Agent PM 的设计决策

- 哪些信息是所有请求的静态基础？
- 哪些信息应由 Router 按意图动态选择？
- 哪些必须实时查询，不能依赖缓存或 Memory？
- Memory 在什么情况下参与组装？
- 不同来源发生冲突时谁优先？
- 如何评估“Context 是否足够且没有多余信息”？

## 工程与产品启发

Context Engineering 的核心原则：

> Context 不是把重要信息都塞进去，而是给出当前推理链真正依赖的信息。

Bad Case 分析时，应分别检查 Router、检索、Tool、Memory、上下文排序与最终生成，而不是笼统归因于“模型不够聪明”。
