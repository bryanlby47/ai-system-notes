# Loop Engineering

## 通俗解释

Prompt 解决一次回答，Workflow 执行固定流程，Loop 让系统根据结果持续推进。

```text
观察
→ 决定下一步
→ 行动
→ 获取反馈
→ 再次观察
```

Loop Engineering 设计的是 Agent 如何循环行动、修正和停止。

## 为什么出现

调试、Coding、Research 等任务无法预先确定需要执行多少步。每次执行都会产生新信息，原计划可能立即失效。

例如修复 Bug：

```text
读代码
→ 修改
→ 测试失败
→ 分析错误
→ 再修改
→ 再测试
```

## 系统模型

```text
Goal
→ Observe
→ Plan
→ Act
→ Feedback
→ Update State
→ Continue / Stop
```

核心设计问题：

1. Observe：Agent 能看到哪些环境信息？
2. Plan：一次规划多远？
3. Act：允许执行哪些动作？
4. Feedback：如何判断动作效果？
5. Stop：什么条件下结束或转人工？

## 核心共识

- Prompt 不再是长任务的主要瓶颈。
- 高频、可靠的外部反馈能够显著提高 Agent 的完成率。
- Loop 必须围绕显式状态运行，否则每轮都像重新开始。
- 停止条件和失败处理与行动策略同样重要。

## 核心 Trade-off

### 长规划 vs 高频反馈

真正的选择不是“规划或不规划”，而是：

```text
长规划 + 低频反馈
vs
短规划 + 高频反馈
```

环境稳定、依赖关系明确时，较长规划更有效；环境不确定、执行会产生大量新信息时，短规划和动态重规划更可靠。

### 自主推进 vs 可控性

循环越自由，覆盖未知路径的能力越强，但成本、风险和调试难度也越高。

### 反馈质量 vs 执行成本

运行测试、查看页面、调用外部工具能够提供更真实的反馈，但会增加时间和计算成本。

## 典型误区

- Loop Engineering 是新的 Prompt 技巧。
- Agent 只要不停循环就会越来越好。
- 规划派希望一次规划完所有未来变化。
- 模型自己说“完成了”就是可靠的停止条件。

## 关键问题

> 为什么 Coding Agent 通常采用短规划和高频反馈？

真正理解的人会分析：代码执行和测试会持续暴露新信息；过长计划容易在前几步后失效，因此需要以环境反馈驱动动态重规划。

## 技术演进位置

```text
Prompt
→ Workflow
→ Loop
→ State Management
→ Agent Runtime
```

## 工程与产品启发

Loop 的本质可以视为动态状态机：

```text
读取 State
→ 选择 Action
→ 执行
→ 获得 Observation
→ 更新 State
```

设计 Agent 时，应优先定义可观测信号、成功标准、失败路径和停止条件，而不是只优化模型提示词。
