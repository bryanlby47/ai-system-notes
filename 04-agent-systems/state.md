# State

## 通俗解释

State 是系统当前记住的事实。

例如外卖订单：

```text
已下单
→ 商家接单
→ 骑手取餐
→ 配送中
→ 已送达
```

系统不是在抽象地“处理订单”，而是在读取并改变订单状态。

## 为什么出现

复杂任务必须知道：

- 目标是什么；
- 已经完成了什么；
- 当前正在做什么；
- 哪些步骤失败了；
- 接下来还需要什么。

如果这些事实没有被记录，每轮模型调用都会像失忆一样重新开始。

## 系统模型

```text
读取 State
→ 决定 Action
→ 执行 Action
→ 获得结果
→ 更新 State
→ 重复
```

Coding Agent 的 State 可能包括：

```json
{
  "goal": "修复登录 Bug",
  "status": "testing",
  "files_changed": ["auth.ts"],
  "failed_tests": ["login.test.ts"]
}
```

## State 和 Memory

```text
State = 当前任务发生了什么
Memory = 长期应该记住什么
```

- State 的生命周期通常是分钟、小时或任务周期。
- Memory 的生命周期可能是周、月或跨任务长期存在。

两者都可能进入模型上下文，但写入策略、读取时机和生命周期不同。

## 核心共识

- 长任务离不开显式 State。
- State 应独立于单次模型推理存在。
- 推理能力不等于状态管理能力。
- Runtime 的核心职责之一是维护可信的 State。

## 核心 Trade-off

### 状态完整性 vs 成本

记录越多，任务恢复和推理越完整；但存储、上下文组装和模型成本越高。

### 自动更新 vs 准确性

自动更新效率高，但错误信息可能污染后续决策；人工确认更准确，但操作成本高。

### 实时状态 vs 长期历史

实时状态适合当前决策，长期历史适合跨任务个性化。混在一起会造成检索和生命周期管理混乱。

## 典型误区

- State 等于 Memory。
- State 等于当前动作。
- 把全部聊天历史塞进上下文就等于维护了 State。
- 模型足够强后不再需要 State。

## 关键问题

> 如果下一代模型推理能力提高十倍，State 还重要吗？

仍然重要。模型能力可以改善“如何判断”，但无法凭空知道哪些文件已修改、任务执行到哪里、外部系统当前返回什么结果。

## 工程与产品启发

几乎所有复杂软件系统都可以抽象为：

```text
State + State Transition
```

设计 Agent 产品时，需要明确 State 的 Schema、所有者、更新时机、可信来源和恢复策略。
