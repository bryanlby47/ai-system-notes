# AI Coding Agent 能力比较与工作流选择

> 状态：草稿（Draft）
> 证据范围：仅本对话可见历史；Codex、Claude Code 的当前产品能力未经核验，本文不构成实测结论。

## 1. 核心问题与初步判断

**用户判断**：“模型一样的话，单就 agent 能力，现在 codex 和 claude code 应该区别不大吧。”

**助手判断（未经实测）**：相同底层模型、相近推理预算与上下文条件下，代码理解、规划、生成等模型侧能力差距可能收窄；但实际任务完成能力仍取决于 Harness、工具反馈、上下文管理、权限机制及长任务执行可靠性。

**认知校准**：“同模型”不等于“同 Agent 能力”；甚至两产品是否允许使用严格相同的模型及配置，也尚未核实。不能据此认定两者当前差异很小或某方更强。

## 2. 分层比较

| 层次 | 比较问题 | 证据性质 |
| --- | --- | --- |
| 模型能力 | 代码理解、规划、推理、生成；模型版本与推理预算 | 用户提出的控制变量；未实测 |
| Harness / Agent Loop | 如何分解任务、选择动作、持续执行、失败后修正 | 助手建议的维度；实现未经核验 |
| 工具与反馈 | 文件搜索、编辑、终端测试、Git 操作，以及错误信息的可诊断性 | 助手建议的维度；未实测 |
| 上下文管理 | 相关文件选择、上下文压缩与恢复、跨步骤状态保持 | 助手建议的维度；未实测 |
| 权限与沙箱 | 命令审批、文件与网络访问、隔离、安全性与人工确认成本 | 助手建议的维度；当前机制未经核验 |
| 长任务可靠性 | 多步执行、纠错、复测、状态延续、任务完成率 | 助手建议的维度；未实测 |
| 产品工程体验 | CLI/IDE、Diff、审阅、Git 工作流、进度与结果可见性 | 助手建议的维度；未实测 |

这些因素相互作用，不能简单视为独立变量。此前助手提出“实际 Agent 能力 ≈ 模型能力 × Harness 能力 × 工具能力 × 上下文管理 × 执行可靠性”，只能当作说明多因素影响的启发式表达，**不是可计算的测量公式**。

## 3. 主要 Trade-off 与待验证假设

- **H1（待验证）**：同模型条件下，边界明确的局部编码任务可能差距较小。
- **H2（待验证）**：跨文件、长步骤、反复测试修正任务更容易暴露 Harness 与上下文管理差异。
- **H3（待验证）**：更少审批可能降低摩擦，但不一定代表更好的安全性；需要同时衡量效率与风险。
- **H4（待验证）**：更丰富的工具反馈可能降低错误恢复成本，但也可能增加上下文占用。

不得把这些假设写成 Codex 或 Claude Code 的已验证产品特性。历史能力描述均未经 2026 年 10 月当前版本核验。

## 4. Spec → Code → Test → Review 工作流

**助手建议，不是用户已确认采用的完整个人开发体系。**

1. **Spec**：明确需求、验收标准、约束与禁止改动范围；观察 Agent 是否正确识别任务与影响面。
2. **Code**：在同一仓库快照中实施变更；观察实现完整性、无关改动和人工干预。
3. **Test**：执行相同测试命令；观察能否解释失败、修复并复测。
4. **Review**：检查 Diff、测试证据、风险说明及未完成事项；衡量审阅与交接成本。

四个阶段是比较视角，不意味着必须建立四个 Agent、四个模块或额外抽象。工具选型优先考虑任务成功、回归风险、人工接管次数与切换成本，而非单纯比较模型回答质量。

**已知对话背景**：助手此前提到 Codex、GitHub 和本地仓库使用场景；但本次对话没有提供足够证据，证明用户已经稳定实施了上述完整流程。

## 5. 最小对比验证（新增建议，尚未执行）

| 测试任务 | 任务设计 | 核心指标 |
| --- | --- | --- |
| A：局部 Bug 修复 | 少量文件，明确回归测试 | 验收通过、无关改动、人工干预 |
| B：跨文件功能 | 多模块修改，固定验收标准 | 完整度、测试闭环、变更质量 |
| C：长任务纠错 | 多轮修改、测试、修复 | 恢复能力、状态保持、人工接管 |

**控制条件**：尽可能固定模型版本、推理预算、初始 commit、提示词、依赖、测试环境、工具权限、运行时间及成本限制。不能对齐时明确记录，比较只能称为“端到端产品比较”，不能严格归因于 Harness。

**记录字段**：产品/版本、模型/配置、任务与验收、初始 commit、执行日志、Diff、测试结果、人工提示次数、审批次数、耗时、消耗、失败类型。

**判断顺序**：先看验收是否达成及回归/安全问题，再看人工接管与错误恢复，最后看耗时、成本和工程体验。避免单次运行就做普遍排名；条件允许时重复测试。

## 7. 重要对话依据

1. **用户原话**：“模型一样的话 单就 agent 能力，现在 codex 和 claude code 应该区别不大吧”——提出比较假设。
2. **助手回应**：“能力差距会明显缩小，但还不能说完全没区别”——未经实测的判断。
3. **助手提出维度**：任务循环、工具反馈、上下文压缩/恢复、文件修改与测试、Git、权限沙箱、失败修正和长任务可靠性。
4. **助手提出验证方式**：“同一个模型、同一个 repo、同一个任务”，比较谁更稳定、谁更少需要人工接管。
5. **助手提出工作流**：Spec → Code → Test → Review；是建议而非已采用事实。
6. **用户沉淀要求**：区分判断、建议、事实与假设；不虚构已采用体系；保护已有内容。

## 8. 已验证事实、知识缺口与结论

**已确认的对话事实**：用户提出同模型假设；助手提出分层比较和工作流验证建议。这不等于相关技术判断已经被实验验证。

**知识缺口**：当前产品版本及模型支持；Harness 和沙箱实现的一手证据；同模型同任务对照日志；用户的真实任务分布、使用成本与切换成本；长任务结果的重复样本。

**草稿结论**：现阶段只能得出研究方向——在尽量控制模型变量后，重点检验 Agent 执行链路与工程体验对任务成功的影响。Codex 和 Claude Code 的实际强弱、差距大小及最终工作流选择，均待验证。
