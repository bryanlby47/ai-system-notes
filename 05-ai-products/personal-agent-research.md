## 1. 通俗解释与结论状态

Personal Agent 可以理解为面向个人、围绕个人目标提供持续协助的 Agent 产品。对于能够跨应用办事的实现，常见底座是模型驱动的执行循环、工具连接、上下文与状态管理，再叠加用户信息、记忆和触发机制。

这是本讨论采用的工作定义，不是统一行业标准。“Personal”描述服务对象与连续性，“自主或受控”描述决策权分配，二者不是同一维度。个人助手可以运行固定流程，业务 Agent 也可以局部自主执行。

| 类型 | 含义 | 本文使用方式 |
|---|---|---|
| 用户明确确认 | 用户明确表达的兴趣、现状或要求 | 不能扩展为用户未确认的架构决策 |
| 助手建议 | 助手提出的解释、判断和方案 | 未经用户明确接受，不记为共同决策 |
| 外部事实 | 一手资料在特定时间披露的内容 | 限于来源和版本，不能据此证明产品效果 |
| 待验证假设 | 尚无充分资料或实验支持的推断 | 保留问题，不包装成事实 |
| 新增建议 | 沉淀时补充、此前未提出的设计或实验 | 与原讨论分开标注 |

当前最重要的判断：

- 【用户明确确认】用户对 Personal Agent 兴趣较浓厚，希望理解其技术逻辑；用户描述自己当前的 Agent 框架比较受控。
- 【助手建议】开放式 Agent 的关键变化，是允许模型在执行中决定下一步，而不只是让回复文本更自由。
- 【助手建议】OpenClaw 是研究完整个人助手系统的合适样本，不应被当作技术上限或统一架构。
- 【待验证假设】Muse、Grokbot 是否采用相似内部实现、是否基于 OpenClaw，均未确认。
- 【助手建议】明确、稳定的任务路径适合受控执行；后续步骤依赖环境反馈的任务可以考虑局部自主执行。
- 【未形成决策】当前对话没有完成框架选型、确定自主范围或证明自主执行的收益。

## 2. 为什么需要 Personal Agent：目标场景与边界

普通问答主要交付信息；能够办事的个人助手还需要访问外部环境、推进任务，并跨轮次维持目标与进度。需求的复杂性在于，用户往往只给目标，实际步骤取决于执行中发现的信息。

原讨论使用的示例是：“帮我整理下周的安排，看看哪些会议值得提前准备。”执行可能需要先读日历，再根据会议内容查文档或相关记录，信息不足时继续检索，最后生成准备建议。这是助手构造的解释性场景，没有实际执行记录。

| 场景 | 可能需要的能力 | 自主执行的潜在价值 | 边界 |
|---|---|---|---|
| 日程与准备建议 | 读取日历、检索文档、汇总 | 按实际会议内容选择资料 | 生成建议不等于修改或取消会议 |
| 跨应用资料整理 | 搜索、读取、生成文件 | 组合未预先枚举的步骤 | 找到资料不等于验证资料可信 |
| 持续项目协助 | 保存进度、检索历史、恢复任务 | 跨对话继续推进 | 历史目标不能覆盖最新用户指令 |
| 定时或事件驱动任务 | 调度、事件入口、结果交付 | 用户不必每次手动发起 | 能触发不等于已授权所有动作 |
| 固定服务流程 | 明确入口、权威数据、固定承接 | 自主性的额外收益可能较小 | 需先证明固定路径存在不足 |

上述场景分类是【助手建议】的整理，不是已确认产品功能或用户的实施需求。

能力边界包括：受限于模型能力、工具可用性、数据质量、权限和资源预算；不能只凭文本判断外部动作完成；记忆不能自动成为授权；主动运行不能自行扩张任务范围；跨应用能力不等于需要云电脑，API、浏览器、终端和设备操作是不同执行方式。

## 3. 系统模型与任务执行机制

### 3.1 决策权如何分配

| 决策 | 受控执行 | 开放式执行 |
|---|---|---|
| 理解任务 | 映射到受控 Intent | 根据目标理解任务，不必先落入固定枚举 |
| 选择能力 | Router 提前决定 Agent、Skill 或路径 | 模型在可用能力中选择，可能按需发现能力 |
| 推进步骤 | 按预定义路径或限定主 Action 推进 | 根据执行反馈拆解、组合和调整步骤 |
| 信息不足 | 按规则澄清、检索或降级 | 模型判断继续查询、换方法或询问用户 |
| 结束执行 | 业务流程与状态决定 | 模型提出结束，Runtime 执行停止与验证约束 |

这张表是【助手解释】，用于说明架构差异；具体实现可能混合两者。[S1] 将预定义代码路径的 Workflow 与模型动态指导过程的 Agent 区分开来，这是该来源的术语口径。

### 3.2 最小执行循环

模型接收目标、上下文和可用工具，输出回复或结构化工具调用请求。Runtime 检查调用、执行工具，将结果或错误交还模型；模型据此决定继续、调整、询问或结束。

模型通常不直接执行操作。工具调用请求、实际执行结果和最终回复是不同事件，需要分别记录。

任务计划可以在执行中变化；不是每个任务都需要独立 Planner、独立评审 Agent 或多 Agent。原讨论没有要求新增这些层。先看是否存在独立职责和工程必要性，再决定实现方式。

【助手建议】需要覆盖的职责包括：

- 明确目标、范围和完成标准。
- 组织每轮上下文与可用能力。
- 执行工具并返回有效反馈。
- 保存进度、控制权限与预算。
- 处理暂停、恢复、失败和结果交付。

这些是职责清单，不是必须拆分的模块清单。

### 3.3 停止与恢复

[S1] 强调根据环境结果评估进展，并设置人工检查点和最大迭代次数等停止条件。[S3] 描述将持久会话与 Harness、沙箱分离，以支持故障后的恢复。

【助手建议】任务完成应基于产物或外部状态；达到预算上限、权限被拒绝、缺少关键输入或工具持续失败时，应明确停止或交还用户。

【新增建议】恢复写操作前先核对上一次是否已生效，避免把“未收到返回”当作“没有执行”。有副作用的操作需要去重或幂等处理，不能只依靠再次生成计划。

## 4. 用户建模、记忆与上下文

### 4.1 用户建模

原讨论只明确提到用户偏好、持续项目和已有授权，没有形成用户模型 Schema、更新流程或实验结果。

【新增建议】将以下信息区分保存，避免混用：

| 信息 | 示例 | 需要的约束 |
|---|---|---|
| 用户显式偏好 | 输出语言、格式、工作习惯 | 可修改，保留来源 |
| 持续目标与项目 | 长期学习任务、正在整理的资料 | 标注状态和更新时间 |
| 情境信息 | 本轮时间范围、临时对象 | 避免自动变成长期偏好 |
| 模型推断 | 可能感兴趣的主题 | 标为推断，不能覆盖显式信息 |
| 授权记录 | 允许访问哪些资源、执行哪些动作 | 独立校验范围、有效期与撤销 |

用户画像帮助理解任务；授权决定能否行动。二者不能合并为“模型认为用户会同意”。

### 4.2 记忆与上下文不是同一个存储对象

【外部事实】[S2] 讨论按需获取信息、上下文压缩和外部笔记；[S3] 区分持久会话日志与模型上下文窗口；[S4] 用上下文内记忆、历史检索和外部知识存储解释 MemGPT 的记忆管理。

【助手解释】系统可以保存很多信息，但每轮只给模型当前相关部分。记忆“存在于系统中”不等于模型本轮已经看到，更不等于检索结果一定正确。

可考虑提前装配确定必需的信息，其他信息按需获取。代价是额外检索耗时、遗漏信息和探索错误。压缩可以减小上下文，但可能丢失后来才显得重要的细节。

【新增建议】记忆应支持来源、时间、纠正和删除；遇到新旧信息冲突时，以明确的新指令为依据，必要时询问用户。不能把一次行为直接推广成稳定偏好。

“长期记忆让 Agent 学习”也需要限定：更新存储与检索策略不等于修改模型参数。

## 5. 工具连接、主动触发、权限与人工确认

### 5.1 工具与执行环境

原讨论提出 API、浏览器、终端和电脑操作等执行方式。MCP 可用于连接工具，但协议本身不能证明工具质量、安全性或任务效果。

【助手建议】工具描述应说明用途、参数、使用条件、返回值与失败方式。过于宽泛或高度重叠的工具会增加选择难度。动态发现或加载能力也不意味着一次把所有工具和 Skill 放入上下文。

Skill 可以提供任务指引，工具执行具体动作；加载 Skill 不会自动获得更多权限。

### 5.2 主动触发

【外部事实，限历史观察】本对话读取的 OpenClaw 官方文档包含 Gateway 事件与自动化相关入口。[S6][S7] 不能据此断言其所有主动任务都可靠完成。

【助手解释】持续运行需要定时或事件机制唤醒执行，模型并非必须一直推理。触发机制决定“何时运行”，任务目标决定“做什么”，权限控制决定“能执行到哪里”。

【新增建议】主动任务应绑定明确的触发条件、目标、预算、交付渠道和停止条件；用户撤销任务或授权后停止运行。默认没有理由把主动触发扩展为无限期自主经营用户目标。

### 5.3 权限与人工确认

【助手建议】Prompt 指引模型应该怎么做；Runtime 在工具执行处控制实际上允许做什么。搜索、读取、写入、发送和不可撤销动作可以采用不同策略，但读取也可能涉及受限数据，不能一概视为无风险。

人工确认不是每一步都询问，也不是一次同意覆盖全部后续动作。确认是否需要，应取决于已有授权、动作影响与可撤销性。

【新增建议】需要确认时，展示具体对象、动作和预期影响；确认内容改变后重新判断授权是否仍适用。将权限拒绝、人工拒绝和工具故障作为不同结果记录。

【外部事实】[S3] 披露通过沙箱与凭据存储分离、工具代理等方式处理凭据边界。本文不把这种设计等同于“已经消除全部安全风险”。

## 7. 不同架构路径与核心 Trade-off

| 路径 | 适用条件 | 主要价值 | 主要代价 |
|---|---|---|---|
| 固定 Workflow / 受控路由 | 目标类别和合法路径稳定 | 可预测、易定位问题、便于业务治理 | 对未知组合覆盖有限 |
| 单 Agent 自主循环 | 后续动作依赖执行反馈 | 动态组合工具、调整路径 | 延迟、成本与错误传播增加 |
| 受控入口 + 局部自主 | 主目标稳定，内部步骤不固定 | 保留边界并容纳探索 | 必须明确局部权限与停止条件 |
| 多 Agent 协作 | 任务有可独立分工的部分 | 隔离上下文、并行或专业分工 | 协调开销、状态冲突、错误交接 |

多 Agent 一项是【新增建议】的比较维度，原讨论没有选定多 Agent 方案。

本地、云端和混合部署是另一条独立轴，不决定执行是否自主。【新增建议】比较它们时应看设备访问、后台运行、数据边界、维护成本和恢复能力，而非仅看部署名称。

自由度、延迟、成本与可靠性存在取舍，但不能假定开放一定更慢或固定一定更好；需在同一任务和预算下验证。自主流程可能减少人工步骤，也可能增加无效探索。

仓库关联阅读：[Loop Engineering](../04-agent-systems/loop-engineering.md)、[Agent Runtime](../04-agent-systems/agent-runtime.md)。

术语提醒：现有 Runtime 笔记采用“Runtime 管调度、Harness 是执行环境”的口径；[S3] 的 Harness 指调用模型和分发工具的循环，Sandbox 才是执行环境。本文按实际职责理解术语，不修改已有笔记，也不认为两种命名天然相同。

## 8. 自主执行的适用条件与受控执行判断

原讨论给出的【助手建议】是：先证明固定路径限制了任务完成，再判断自主执行能否被验证和控制。这是架构选择条件，不是构建自主循环的物理必要条件。

| 条件 | 判断问题 |
|---|---|
| 目标和边界明确 | 要完成什么，哪些动作不属于本次任务？ |
| 动态决策有收益 | 下一步是否依赖刚获得的信息？稳定流程能否同样解决？ |
| 工具反馈有效 | 能否知道操作成功、失败或状态不确定？ |
| 错误代价可控 | 能否撤销、限制权限或在关键动作前确认？ |
| 完成情况可验证 | 是否有独立于模型自述的产物或状态依据？ |
| 模型能力经验证 | 实际工具集下是否能正确选工具、填参数和处理失败？ |

受控执行更适合固定合法路径、权威业务规则、时延要求明确、错误代价高的任务。是否金融场景、是否叫“助手”，都不足以单独决定架构。

原讨论的局部自主例子是“为什么还款失败”：若后续查询依赖交易记录、银行卡状态、错误码等中间反馈，可以在限定目标内动态查询；原因仍以权威数据为准，资金操作仍受控制。如果已有稳定接口直接返回原因，固定路径可能更合适。这是【助手构造的示例】，不是已确认的业务需求或实现。

开放的单位可以是一个 Skill 内的一段过程，不必是整个 Agent。工具失败允许重试或降级，不应自动成为改变主目标的理由。

## 9. 失败模式与验证方法

以下是对原讨论风险点的具体化；去重、冲突与注入等细节属于【新增建议】，均未在本次执行验证。

| 失败模式 | 可观察表现 | 验证方法 |
|---|---|---|
| 目标漂移 | 主动扩展范围或更换目标 | 对照用户目标和授权逐步检查 |
| 错误工具或参数 | 用错对象、时间范围或资源 | 核对真实调用与预期状态 |
| 低质量反馈 | 将超时当失败，将返回文本当成功 | 注入失败与不确定状态，检查后续行为 |
| 无限重试或提前结束 | 无进展消耗预算，或产物未完成就结束 | 记录每步进展、停止原因与最终产物 |
| 记忆误用或遗漏 | 旧偏好覆盖新指令，检索无关历史 | 设计纠正、冲突与无关信息样例 |
| 重复副作用 | 恢复后重复写入或发送 | 模拟返回丢失与进程中断 |
| 权限或确认失效 | 拒绝后仍执行，确认对象发生变化 | 检查执行端拦截和审计记录 |
| 外部内容影响指令 | 将网页或文件中的文字当成授权 | 使用合成注入内容，检查边界 |
| 受控流程覆盖不足 | 合法目标被拒绝或错误降级 | 使用真实需求分布验证拒识与承接 |
| 主动触发失控 | 重复触发、撤销后仍执行、过度打扰 | 检查触发、取消、去重和交付 |

验证应同时看结果、过程和成本。不能只看回复质量，也不能强制自主 Agent 与标准答案使用完全相同的路径。

建议记录：任务完成率、事实正确性、越权情况、人工介入次数、无效工具调用、耗时、费用、恢复成功率，以及模型声称完成与实际完成的差异。指标定义和阈值应按任务确定，本讨论尚未给出可用基线。

对照实验应尽量固定模型、数据、工具、权限和预算，重复运行以观察波动；把模型问题、工具问题、上下文问题和 Runtime 问题分开归因。

## 13. 不超过三个最小验证实验

以下三项全部是【新增建议】，不是原讨论已确认或已执行的实验。先用合成数据、只读工具和模拟副作用，减少无关变量。

### 实验一：动态路径是否真的有收益

构造 12 个日程准备任务：6 个可以固定步骤完成，6 个需要根据查询结果选择后续资料。使用相同模型、工具、数据与预算，对比固定 Workflow 和单 Agent 自主循环，各重复三次。

核对最终建议是否覆盖正确会议和必要资料，同时记录完成率、错误、工具次数、耗时与费用。若收益只发生在动态任务中，支持局部自主；若没有收益，不支持仅因“更通用”而扩大自由度。

### 实验二：记忆是否改善连续性

用同一组合成用户信息构造跨会话任务，包含明确偏好、后来纠正、临时信息和无关历史。对比仅当前会话、简单历史摘要、带来源的按需记忆三种方式。

检查有效信息是否被正确使用、旧信息是否被纠正、临时信息是否被错误长期化、无关信息是否干扰任务。该实验检验具体记忆策略，不声称覆盖全部个性化能力。

### 实验三：主动触发、确认与恢复是否守住边界

在沙箱中配置一次定时触发任务，涉及读取资料和模拟发送。注入重复触发、工具超时、结果已生效但返回丢失、人工拒绝、确认后对象改变、授权撤销和进程中断。

检查取消是否生效、是否重复执行、确认是否绑定具体动作、恢复后是否先核对状态，以及最终报告是否与实际记录一致。任何越权或重复副作用都应阻止扩大该动作的自主权限。
